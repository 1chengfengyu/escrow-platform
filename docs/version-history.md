# 版本演进

项目从空仓库推进到可用系统，按「先闭环、再加固、再扩展」分版。每一版都能独立验收，也都留下了明确的技术债与后续项（见 [limitations.md](limitations.md)）。

## 技术栈引入顺序

中间件不是一次性堆进去的，每一样都在它真正被需要的那一版加入，并且默认可以不启动。

| 版本 | 引入 | 为什么是这一版 |
|---|---|---|
| V0 | MySQL、Redis、Flyway、Docker Compose | 先有可重复的本地环境，再写业务 |
| V1 | Spring Session + Redis、BCrypt、登录限流 | 会话与限流在第一个登录接口出现时就需要 |
| V2 | 复式记账、条件更新、幂等键 | 「发布即托管」要求资金与名额同一事务 |
| V5 | Nacos 配置中心、结构化日志、通知 | 通道模式与重试参数要能改完不重启 |
| V6 | MongoDB | 对账报文半结构化、只追加、按日期查 |
| V8 | Kafka、死信、降级写库 | 站内信不能阻塞主流程，也不能丢 |
| V9 | Caffeine 两级缓存、ShedLock | 读多写少 + 定时任务多实例互斥 |
| V10 | Spring AI、DeepSeek 兼容接入 | AI 只是检索链路上的一层，可与规则基线并存 |
| V12 | Vue 3 + TypeScript + Vite | 后端契约稳定后再做前端，避免反复改接口 |

没有引入的组件（Seata、Dubbo、Sentinel、SkyWalking、Arthas、Kubernetes、Elasticsearch、向量库）及逐项理由见 [tech-stack.md](tech-stack.md) 的「评估过但没有采用」一节。

## 关键转折

### V2：为什么「发布即托管」

最初把「创建任务」和「冻结报酬」分成两步，结果是：任务已经可以被报名，但钱还没冻结；或者钱冻结了，名额没生成。两者之间任何一步失败都会留下脏状态。

V2 改成同一个本地事务：生成名额、创建托管单、写冻结分录、更新余额，要么全成，要么全不成。这是整个资金链路最重要的一个决定。

### V5：为什么打款要单独建模

打款不是「调用一次接口」：通道超时的时候，钱可能已经出去了，也可能没有。直接把超时当失败重试，会重复打款；直接当成功，会漏款。

V5 把打款拆成「业务意图（payout_order）+ 通道查询（payout_verification）+ 人工决策（payout_manual_decision）」，超时进入执行中，由查询结果决定下一步，仍不确定才转人工。状态机不允许从「执行中」直接重试。

### V7：为什么安全不是最后做

早期把限流、脱敏、审计、越权告警全排在最后，导致前面每一版都在积累「先这样，以后再补」的债。V7 集中补齐后发现，很多改动要回头改已有接口。

之后的版本把安全基线前置：新增接口必须同时提交权限矩阵、错误码、审计字段与脱敏规则，否则不进入验收。

### V10：为什么 AI 要有 stub

如果 AI 只能调真实模型，CI 会依赖外部服务，评测无法复现，本地开发没有 key 就跑不起来。V10 把规则实现做成完整基线（槽位、排序、抽取式答案），模型只是可选的增强层。

这样做的副作用是：「AI 功能」在无 key 时仍然可用，只是标 `degraded=true`。对演示和回归测试都是好事。

### V12：为什么前端最后做

前端 53 个路由不是难点，难点是让每个页面都对应真实接口、真实状态与真实权限。先做后端契约测试，再做前端，页面只需要消费已经稳定的响应体；反过来做，会不断改接口去迁就页面。

## 版本号说明

公开仓库只打一个 `v1.0.0` 标签。V0–V12.1 是开发阶段的内部里程碑，保留在本文件中，不逐一打 tag——避免出现一堆没有发布意义的空标签。

`pom.xml` 与 `frontend/package.json` 的版本号统一为 `1.0.0`。
