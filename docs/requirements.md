# 1. 引言

## 1.1 编写目的

本文档定义「灵活用工任务结算与报酬托管平台」（下称"本系统"）v1.0 的软件需求，作为设计、开发、测试与验收的唯一依据，同时作为需求变更的基线。

**读者对象**：开发者（本人）、评审者、测试执行者、AI 编码助手。

## 1.2 范围

### 1.2.1 产品定位

本系统是一个**零工任务的撮合与资金托管平台**。雇主发布任务并预先托管资金，劳动者接单履约，雇主验收后由平台将资金结算给劳动者。系统解决的核心问题不是"信息不对称"，而是**履约不信任**——通过资金先到位，把"我不给你钱"与"你不给我干活"两个风险同时压住。

### 1.2.2 包含（本期必做）

| 编号 | 内容 |
|---|---|
| S-01 | 三端：雇主端、劳动者端、管理端（同一后端，三套前端路由） |
| S-02 | 六个功能域：账号与资质、任务发布与检索、签约与履约、资金、争议与信誉、通知与调度 |
| S-03 | 1 任务 N 个平行名额（名额间无协作、无分账、无主从） |
| S-04 | 平台余额记账体系（与人民币 1:1，六科目，借贷分录） |
| S-05 | 模拟支付通道（可注入成功/失败/超时/响应丢失/重复回调/通道漏记/金额不符七种模式） |
| S-06 | 全额托管、全额退款、日终对账、差异单 |
| S-07 | 争议仅冻结 + 人工处置（放款 / 退款 / 发起方撤回） |
| S-08 | 定时任务：自动验收、到期下架、打款重试与查证、未开始自动取消、日终对账 |

### 1.2.3 不包含（本期明确不做）

| 编号 | 不做 | 理由 |
|---|---|---|
| NS-01 | 真实支付、真实提现、银行卡绑定 | 需企业主体资质，个人不可获得；且非本项目技术目标 |
| NS-02 | 发票、个税代扣、社保代缴 | 税务是独立领域，做不透反减分 |
| NS-03 | 多人协作任务、班组、分包、转包 | 会把结算变成分账，复杂度翻倍 |
| NS-04 | AI 自动裁决争议 | 不可解释、不可复现，资金决策不能交给模型 |
| NS-05 | 部分退款 / 部分验收 | 引入拆分结算，本期不支持 |
| NS-06 | 定金 + 尾款两段付款 | 见附录 D 决策说明 |
| NS-07 | 推荐算法、个性化首页 | 与"钱不出错"无关 |
| NS-08 | 多租户 SaaS、开放 API | 无需求来源 |
| NS-09 | 微服务拆分 | 资金一致性靠本地事务即可，拆分会把问题升级为分布式事务 |
| NS-10 | 微信小程序端、精美 UI | 首版不做，避免挤占主线 |
| NS-11 | 私聊中的联系方式拦截 | 本期仅做提示，不做拦截（见 3.6.1 FR-MSG.CHAT.03） |
| NS-12 | 浏览量/访客记录（"谁看过我的任务"） | 属招聘站功能，对资金链路无贡献，且涉及隐私 |

## 1.3 术语与缩略语

| 术语 | 定义 |
|---|---|
| **任务（Task）** | 一次用工需求，由雇主发布，含标题、单价、名额数、起止时间 |
| **名额（Slot）** | 任务的可承接单位。1 任务含 N 个名额，每个名额独立签约、独立结算 |
| **签约（Contract）** | 雇主录用某劳动者承接某名额所形成的约定关系 |
| **平台余额** | 用户在系统内的记账金额，与人民币 1:1，最小单位"分"。仅用于平台内托管与结算 |
| **可用余额** | 可发起托管、可申请模拟提现的部分 |
| **冻结余额** | 已托管、尚未释放的部分，用户不可支配 |
| **报名（Application）** | 劳动者对某任务表达承接意愿的记录，不占名额；雇主从中录用 |
| **托管单（Escrow）** | 记录"平台代持一笔资金"的单据，与任务 1:0..1（草稿阶段不存在） |
| **托管明细（EscrowItem）** | 托管单按名额拆分的冻结记录，与名额 1:1，是释放/退款的最小单位 |
| **结算单（Settlement）** | 记录"应给某劳动者多少、平台收多少"的单据，与名额 1:0..1（未验收则不存在） |
| **打款单（Payout）** | 记录"一次对外付款**尝试**"的单据，与结算单 1:0..N（每次重试一张） |
| **在途资金** | 已发起打款、尚未取得确定结果的部分 |
| **发行总额** | 系统累计投放的平台余额总量，只增不减，是账务的锚。**全局唯一一份，不属于任何用户** |
| **模拟通道** | 系统内部实现的支付通道替身，可返回成功、失败、超时、响应丢失等七种模式 |
| **模拟提现** | 将可用余额转出至"已提现"科目的账务动作，不涉及任何真实银行账户 |
| **业务幂等键**（`payment_intent_no`） | 保证"同一笔应付至多成功一次"的业务级标识。本系统取**结算单号**，一旦生成终身不变 |
| **请求号**（`payout_request_no`） | 标识"一次物理打款请求"的标识。每次实际发起（含重试）都重新生成，通道按它去重 |
| **凭证批次**（`journal_batch_id`） | 一次业务动作产生的全部分录所属的批次号，同批次借贷必平 |
| **EARS** | 需求句式模板（When/While/Where/If + shall） |
| **TBD** | 待定问题（To Be Determined） |

# 2. 总体描述

## 2.1 产品前景

### 2.1.1 系统上下文

```
        ┌──────────┐        发布/验收/争议          ┌──────────────┐
        │  雇主    │◀─────────────────────────────▶│              │
        └──────────┘                                │              │
                                                    │   任务托管    │
        ┌──────────┐        检索/接单/交付/申诉      │   结算平台    │
        │ 劳动者   │◀─────────────────────────────▶│              │
        └──────────┘                                │              │
                                                    │              │
        ┌──────────┐        审核/处置/查询           │              │
        │ 平台运营 │◀─────────────────────────────▶│              │
        └──────────┘                                │              │
                                                    │              │
        ┌──────────┐        打款请求/结果/流水       │              │
        │ 模拟通道 │◀─────────────────────────────▶│              │
        └──────────┘                                └──────────────┘
                                                          ▲
                                              ┌───────────┴──────────┐
                                              │   定时调度器（内部）  │
                                              └──────────────────────┘
```

**外部实体**：雇主、劳动者、平台运营、模拟通道。
**内部组件**：定时调度器（触发自动验收、到期下架、打款重试、日终对账）。

> 模拟通道必须作为**外部实体**建模，因为它是"通道账"的来源，是日终对账的另一方。若把它视为系统内部组件，对账将退化为自证。

### 2.1.2 与既有系统的关系

本系统为独立系统，不依赖任何既有业务系统。模拟通道为内部实现的替身服务，不连接任何真实支付机构。

## 2.3 用户类别与特征

### 2.3.1 人类用户

| 用户类别 | 使用端 | 优先级 | 描述 | 技术水平 | 频次 | 核心目标 | 权限范围 |
|---|---|---|---|---|---|---|---|
| **雇主** | 雇主端 | 重点 | 个体工商户、小微商户、个人雇主 | 中 | 周 | 钱压得住，人不来能退 | 发布/录用/验收/申诉/查看本方资金 |
| **劳动者** | 劳动者端 | 重点 | 灵活就业者、兼职者、临时工 | 低–中 | 周 | 干完能确定拿到钱 | 检索/报名/交付/申诉/查看本方资金 |
| **平台运营** | 管理端 | 次要 | 项目所有者（模拟） | 高 | 日 | 有据可依地放款或退款 | 审核资质/处置争议/处理差异单/查询审计 |
| **财务审计** | 管理端 | 次要 | 项目所有者（模拟） | 高 | 日 | 每一分钱都能追到单据 | 只读：对账报告、资金流水、审计记录 |

### 2.3.2 系统参与者

| 参与者 | 触发什么 | 说明 |
|---|---|---|
| **定时调度器** | 自动验收、到期下架、未开始自动取消、打款重试与查证、日终对账 | 触发的状态变更，审计 `trigger_source` 必须记为 `SYSTEM` |
| **模拟通道** | 响应打款请求、推送回调、提供流水查询 | 可返回成功/失败/超时/响应丢失/通道漏记/金额不符 |

> 自动验收与人工验收在任务状态机上产生同一结果，但审计必须可区分。否则争议时无法回答"这笔钱是雇主的真实意思，还是系统替他决定的"。

## 2.4 运行环境

| 项 | 要求 |
|---|---|
| 服务端语言 | Java 17（LTS；`pom.xml` 设定 `maven.compiler.release=17`） |
| 框架 | Spring Boot 3.5.16（Spring Framework 6.2.x 由 BOM 管理） |
| 构建工具 | Maven 3.9+（单模块，不拆多模块） |
| 数据库 | MySQL 8.0.42（单库，utf8mb4，表结构只由 Flyway 管理） |
| 缓存 | Redis 7.4（会话、限流、缓存、分布式锁，不承载账务） |
| 消息与归档 | Kafka 3.x（KRaft）、MongoDB 7（对账报文归档），按 profile 启用 |
| 客户端 | Chrome / Edge 最新两个大版本；最低分辨率 1366×768 |
| 网络 | 本地或内网访问；不要求公网可达（模拟通道不回调外部地址） |
| 部署形态 | 单机 Docker Compose（MySQL + Redis 默认启用，Kafka / MongoDB 按 profile 追加） |
| 开发工具 | IntelliJ IDEA；需求文档与代码同仓，置于 `docs/` |

**可选集成的验证方式**：若需增强"支付协议"的真实感，可另行接入支付宝沙箱作为充值入口的验证手段。**该集成不属于本 SRS 范围**，不影响本系统任何需求的验收。

**为什么锁定 Spring Boot 3.5.16 而不是 4.x**

选型依据是依赖组合的可复现性，而不是框架版本号本身：

| 依赖约束 | 结论 |
|---|---|
| Spring AI 1.1.8 要求 Boot 3.x / Framework 6.x / Jackson 2.x | 升到 4.x 必须同时迁移 Spring AI 2.x 与 Jackson 3 |
| MyBatis-Plus 3.5.18 的 Boot 3 starter 只覆盖 Boot 3.x | 4.x 需等待官方 starter |
| 单体架构不依赖 Framework 7 的新特性 | 升级收益为零，代价是全量回归 |

3.5.16 是 3.5 线末版，OSS 补丁已停止。本项目定位为本地演示与工程验证，不接公网、不处理真实资金，因此接受该代价。若后续要长期维护，升级路径是 Boot 4.x + Spring AI 2.x + Jackson 3 一次性迁移，见 `docs/limitations.md` 第 7 节。
## 2.5 设计与实现约束

| 编号 | 约束 | 依据 |
|---|---|---|
| CR-01 | 采用**单体架构**，单库单应用，资金一致性由**本地事务**保证 | 拆微服务会把本地事务升级为分布式事务，用复杂度换减分 |
| CR-02 | 所有金额以**最小货币单位（分）**的 64 位整数存储与运算 | 浮点累加会丢分，1 万笔后对账永不平 |
| CR-03 | 金额字段禁止使用 `float` / `double`；展示层才转为元 | 同上 |
| CR-04 | 支付与打款通过**模拟通道**完成，不得接入任何真实支付机构 | 真实支付需企业主体资质；且本项目目标是资金一致性而非渠道对接 |
| CR-05 | 不得实现真实提现，不得调用银行代付、企业付款等真实资金转移接口 | 避免越界为真实支付业务 |
| CR-06 | 账务采用**六科目 + 借贷分录**记账，分录为账务唯一真相，余额字段是分录的物化结果 | 便于定位"哪一步错了"而非"余额对不上" |
| CR-07 | 平台余额与人民币 1:1 计价，不设汇率、不做兑换 | 保持语义简单 |
| CR-08 | AI（大模型）**仅用于**任务检索的语义重排与文案生成；**不得**参与金额计算、状态判定、争议裁决 | 资金决策必须可解释、可复现 |
| CR-09 | 采用**全额托管**：任务发布时一次性冻结"单价 × 名额数"；不做定金+尾款 | 见附录 D |
| CR-10 | 争议仅支持**全额放款**或**全额退款**两种终局；不支持部分退款 | 部分退款需拆分结算，复杂度显著上升 |
| CR-11 | 每个名额独立生成结算单，独立打款 | 与"1 任务 N 名额"模型一致 |
| CR-12 | 允许同一账号同时具备雇主与劳动者身份，需"当前身份"上下文 | 零工场景常见（小老板自己也接活） |
| CR-13 | 服务费率、自动验收时长、打款重试上限（`payout.maxAttempts`，默认 3）、执行中滞留阈值（`payout.stuckMinutes`，默认 10）、**待执行滞留阈值（`payout.pendingMinutes`，默认 2）**、接单后未开始挂起时长应可配置 | 便于测试与调参；重试上限为**单张结算单的尝试总上限**，自动重试与人工受控重发共用；两个阈值分别驱动 `FR-JOB.PAYOUT.01` 的出站与转未知分支 |
| CR-14 | 需求文档与代码同仓，置于 `docs/` | 便于评审与追溯 |
| CR-15 | **同一账号不得报名或承接自己发布的任务**（自我交易禁止） | 双身份允许后若不禁自我交易，演示数据会自导自演，污染履约与信誉统计；如需放开见 TBD-07 |
| CR-16 | 资金类对象的**接口枚举与审计日志必须带对象类型前缀**（如 `SLOT_*` / `SETTLEMENT_*` / `PAYOUT_*`）；中文展示名允许复用，但必须由对象上下文限定（如"名额已释放""托管已释放"），不得单独出现 | 五个状态机共存，同名状态会让日志与 UI 无法定位对象 |

## 2.6 假设与依赖

| 编号 | 类型 | 内容 | 若不成立的影响 |
|---|---|---|---|
| A-01 | 假设 | 容量口径统一为：**任务 10 万、名额 50 万、资金流水 100 万、并发 20**。该口径即 `NFR-PERF.01~03` 的验收数据规模 | 若实际量级超过 2 倍，需重新评估索引、分页与对账批处理窗口 |
| A-02 | 假设 | 定时调度器与应用同进程部署（如 Spring `@Scheduled`） | 多实例部署时需引入分布式锁，否则任务重复执行 |
| A-03 | 假设 | 模拟通道与应用同进程（同库或独立表） | 若拆为独立进程，需增加服务发现与超时配置 |
| A-04 | 假设 | 单机部署，无跨节点时钟偏差 | 超时判定依赖服务器本地时钟 |
| A-05 | 依赖 | 数据库事务隔离级别不低于**可重复读（REPEATABLE READ）**，且资金账户读写使用行级锁 | 隔离级别不足会导致并发下的余额幻读与超冻（见 FR-ESCROW.HOLD.04） |
| A-06 | 依赖 | 用户已完成实名注册（本期仅记录，不做三方核验） | 若需真实核验，需接入三方服务 |

| ACC-WITHDRAWN | 已提现 | **系统唯一一条** | 资金出口（模拟） | **贷** |
| ACC-ISSUED | 发行总额 | **系统唯一一条** | 系统投放总量，只增不减 | **借** |

> **「正常余额方向」这一列不是装饰，是分录写法的唯一依据**（v1.4 的 P0-03）。本系统的六个科目是同一张复式账的两侧：`ACC-ISSUED` 是"钱从哪来"（借方），其余五个是"钱现在在哪"（贷方），恒等式 `ACC-ISSUED(借) = 其余五项之和(贷)` 就是借贷平衡本身。由此得出一条**全文通用的记账约定**：
>
> > **借 = 流出方（该科目余额减少）；贷 = 流入方（该科目余额增加）。**
>
> 任何一条资金路径，先按 A.4 找到"从哪个科目出、进哪个科目"，再按本约定写成"借出的科目 / 贷进的科目"。**若出现"借流入方、贷流出方"，一律是写反了**——最典型的错法是把 `在途→冻结` 写成"借冻结 / 贷在途"（v1.3 的 `FR-PAY.MANUAL.03` 与 3.4.6 就犯过这个错）。
>
> **只看"余额含义"列是写不出分录的**：它是业务语义（"这笔钱能干什么"），不含方向信息；方向只在本列。此前缺这一列，导致同一种 `在途→冻结` 在 3.4.6 内部前后写法相反，实现者无法自证对错。

> **账户归属规则**：账户记录必须带 `owner_type`（`USER` / `SYSTEM`）。`ACC-AVAIL`、`ACC-FROZEN` 为每用户各一条；其余四个科目为**全局唯一**的系统科目，不随用户复制。若把 `ACC-ISSUED` 按用户拆分，恒等式会把同一份发行总额重复累加，账永远不平。

**账务恒等式（对账唯一判据）**

```
ACC-ISSUED 总额 = Σ ACC-AVAIL + Σ ACC-FROZEN
                + ACC-PLATFORM + ACC-TRANSIT + ACC-WITHDRAWN
```

> 式中 Σ 表示对所有用户求和；`ACC-PLATFORM` / `ACC-TRANSIT` / `ACC-WITHDRAWN` 为系统科目，各只取一条，不参与求和。

> **为何禁止人工直接重发「未知」单据**：打款单进入「待人工处理」可能源于两种前提——"结果未知"或"已确认失败"。前者通道侧可能已扣款，直接重发会造成真实二次扣款；后者才可安全重发。因此本节的处置入口只对「已确认失败」（由 FR-PAY.MANUAL.03 之后的状态）开放，`UNKNOWN` 必须先经查证或人工定性，不得跳过。

**差异处置的借贷映射（v1.2 的 P1-04）**

符号：`S` = 该名额应结金额（= 冻结额 = 在途额）；`F` = 结算单服务费；`X` = 打款单请求金额（`X = S − F`）；`Y` = 通道实际出款金额（`actual_amount`）。

| 差异 | 处置 | 借方 | 贷方 | 前置校验与限制 |
|---|---|---|---|---|
| ① 本地成功 / 通道无记录 | **冲正 + 回退重试** | 收款人可用 `X`；平台收入 `F` | 在途 `S` | ① 必须取得通道"零出款"确认；② 收款人可用余额须 ≥ `X`，不足则差异单保持「待处理」并升级，**不得透支、不得从冻结补**；③ 冲正后须再做 `在途→冻结`（**借在途 `S` / 贷冻结 `S`**），并**同步把四个对象一起退回**：打款单「成功」→「失败」（定向更正 `SUCCESS_REVERSED`）、结算单「已完结」→「待重试」、名额「已完结」→「待结算」、托管明细「已释放」→「释放中」。四处缺一不可，只退账不退单据会让单据停在终态却还能再出款 |
| ① 本地成功 / 通道无记录 | 忽略并说明 | — | — | 仅当核实"通道实际已出款、流水丢失"时允许；须附通道侧凭据，不生成任何分录 |
| ② 通道成功 / 本地未知 | **补记** | 在途 `S` | 收款人可用 `Y`；平台收入 `F`；雇主可用 `X − Y`（仅当 `Y < X`） | `Y = X` 时正常；`Y ≠ X` 需同时生成③的差异单。补记后打款单→「成功」（写 `actual_amount = Y`）、结算单→「已完结」、名额→「已完结」、托管明细→「已释放」 |
| ③ 金额不一致（入账前） | **按实际金额入账** | 在途 `S` | 收款人可用 `Y`；平台收入 `F`；雇主可用 `X − Y`（仅当 `Y < X`） | 两侧之和必须等于 `S`；`Y > X` 时**不允许按多付入账**，一律转「待处理」并升级（通道多付须向通道追偿，平台不得垫付） |
| ③ 金额不一致（已按 `X` 入账后才发现） | **差额调整** | 收款人可用 `X − Y`（`Y < X`） | 雇主可用 `X − Y` | 只做差额、不做整笔冲正；收款人可用不足时差异单保持「待处理」并升级，不得透支 |
| 任意 | 忽略并说明 | — | — | 只归档说明，**不生成任何分录**（不得凭空造 0 元或占位分录） |

> **为什么每类都要给出科目而不是只写"补记/冲正"**：只写动作名，实现者会按各自理解挑科目——最典型的是把差额记进平台收入，看起来恒等式仍为 0，实际是把雇主的钱记成了平台的收入。上表把"钱从哪个科目出、进哪个科目"钉死，`AC-07` 才能验到分录层。
>
> **冲正不改变单据状态**：账务冲正是记账动作，与业务状态迁移分开。① 的"回退重试"是**唯一**需要动单据状态的场景，且必须按上表把 `在途→冻结` 一并做完，否则在途留下无出口余额。
>
> **① 的回退要动四个终态，缺一张表的迁移就实现不出来**（v1.4 的 P0-02）。① 的前提是"本地已按成功入账"，此时**打款单「成功」、结算单「已完结」、名额「已完结」、托管明细「已释放」四个对象都已在终态**。v1.3 只在此处用一句话承诺"回退重试"，四张状态机表里却**一条出边都没有**——按表实现，这个处置根本不可达。v1.4 在 A.3.1 / A.3.3 / A.3.4 / A.3.5 各补一条 `差异① 回退重试` 迁移，四张表的"终态不变"行同时加例外脚注。**这四条是整个系统里唯一允许从终态迁出的边**，实现时必须满足三个约束：① 只能由差异单的「冲正」处置驱动，无其他入口；② 必须记 `SUCCESS_REVERSED` 审计并计入告警；③ 四条迁移在同一事务内完成，不允许部分成功。不得推广成通用的"撤销"能力。

**判定树：争议终局**

```
争议终局（穷举，无第四种）
├─ 发起方撤回（管理员作出裁决之前，不以是否查看/受理为条件）
│   └─ 冻结 → 已托管，名额 待裁决 → 已交付，重新起算验收倒计时
├─ 判定劳动者履约成立 → 全额放款（冻结 → 释放中 → 已释放，名额 → 待结算 → 已完结）
├─ 判定劳动者履约不成立 → 全额退款（冻结 → 已退款，名额 → 已退款）
└─ 若判定需部分退款 → 本期不支持，转人工线下处理，争议单标记「超范围」
```

# 4. 数据需求

## 4.1 逻辑数据模型

```
用户 1 ──── N 任务（发布）
任务 1 ──── N 名额
任务 1 ──── 0..N 报名
用户 1 ──── N 报名（提交）
名额 1 ──── 0..1 报名（录用时回填）
名额 1 ──── 0..1 签约
用户 1 ──── N 签约（承接）
任务 1 ──── 0..1 托管单
托管单 1 ── N 托管明细（每名额一条）
名额 1 ──── 0..1 结算单
结算单 1 ── 0..N 打款单（每次尝试一条）
名额 1 ──── 0..N 争议单（同一时刻至多 1 张「待裁决」）
争议单 1 ── N 争议证据
用户 1 ──── N 账户（仅 AVAIL / FROZEN 各一条）
凭证批次 1 ─ N 分录
账户 1 ──── N 分录（分录必须带 account_id）
用户 1 ──── N 消息 / 会话
```

**基数说明**

| 关系 | 基数 | 说明 |
|---|---|---|
| 任务 : 名额 | 1 : N | N ∈ [1, 20]，创建时一次生成 |
| 任务 : 报名 | 1 : 0..N | 草稿与无报名时为空 |
| 名额 : 报名 | 1 : 0..1 | 仅被录用时关联，其余报名保持「待处理/已拒绝」 |
| 名额 : 签约 | 1 : 0..1 | 未录用或已取消时为空 |
| 名额 : 结算单 | 1 : 0..1 | 未验收（或被拒收）时不存在；判定放款时首次创建 |
| 结算单 : 打款单 | 1 : 0..N | **每次尝试一条**，含每次重试与受控重发；实付为 0 时为 0 条 |
| 任务 : 托管单 | 1 : 0..1 | 草稿阶段不存在 |
| 托管单 : 托管明细 | 1 : N | 每名额一条，便于独立释放与退款 |
| 名额 : 争议单 | 1 : 0..N | 撤回后复用同一张（撤回次数累加），因此正常流程只有 1 张；允许 N 是为了容纳"撤回后再次发起"的历史 |
| 争议单 : 争议证据 | 1 : 0..N | 双方均可上传 |
| 账户 : 分录 | 1 : N | **分录必须带 `account_id`**，否则同一科目下多用户账户无法区分，`NFR-CONSIST.02` 的"按分录重建余额"不可实现 |
| 凭证批次 : 分录 | 1 : N | N ≥ 2，同批次 `SUM(DEBIT)=SUM(CREDIT)` |

## 4.2 数据字典

### 4.2.1 核心数据项

| 数据项 | 类型 | 约束 | 说明 |
|---|---|---|---|
| 发生额 | long（分） | **> 0** ~ 999,999,999 | 一次资金动作的变动量；**金额为 0 的科目不生成分录**（如服务费为 0 时的贷方行），不得写入 0 元分录；不得参与浮点运算 |
| 余额 | long（分） | **≥ 0** ~ 999,999,999 | 表示某时点的结存；允许为 0（如实付为 0 的结算） |

| 业务幂等键 `payment_intent_no` | varchar(32) | 全局唯一，取结算单号 | 保证一笔应付至多成功一次；重试不变 |
| 请求号 `payout_request_no` | varchar(32) | 全局唯一，每次尝试新生成 | 通道按它去重；不得复用 |
| 凭证批次号 `journal_batch_id` | varchar(32) | 全局唯一 | 一次业务动作的全部分录同属一批，批内借贷必平；实现列名 `batch_no`，见 `docs/decisions.md` #14【V2 补充】 |

| 履约记录 | ID、劳动者ID、签约ID、事件类型（开始/交付/取消/超时取消）、时间 | 只追加；用于 FR-SIGN.START.02 计入履约记录 |
| 配置项 | 键、值、变更人、变更时间 | — |

> **凭证批次的借贷平衡如何保证**：分录只允许经**唯一一个记账服务**写入，提交批次前校验 `SUM(DEBIT)=SUM(CREDIT)`，不平则拒绝提交；数据库层可用延迟约束（`DEFERRABLE INITIALLY DEFERRED`）或触发器兜底。SRS 只规定"必须平衡且不得有 0 元分录"，具体落地方式在概要设计确定。
>
> **分录必须带 `account_id`**：同一科目下存在多个用户账户（如 `ACC_AVAIL` 每人一条），只记"科目"无法归属；`NFR-CONSIST.02` 要求"以分录为准重建余额"，没有 `account_id` 就重建不出来。科目字段保留作冗余校验。
>
> **打款单为什么"不对结算单ID加唯一约束"，却又要求"至多一条成功"**（v1.2 的 P0-02）：一张结算单可以有多次尝试，故不能对 `结算单ID` 整体唯一；但成功必须唯一。因此约束不能写成行级唯一，而应写成**部分唯一索引**：`UNIQUE (结算单ID) WHERE 状态 = '成功'`（不同数据库语法不同，语义等价即可）。这条索引是 `NFR-CONSIST.03`（同一 `payment_intent_no` 成功入账次数为 1）在存储层的兜底，**不得省略**。
>
> **`actual_amount` 为什么必填于成功态**：通道可能按与请求不同的金额出款（`AMOUNT_MISMATCH`）。若只记请求金额，人工判定成功时只能按请求金额入账，差额既无账务归属也无法回收；判定失败时又按请求金额退款，而通道已付出实际金额——形成重复出款（v1.2 的 P0-01）。因此**状态为「成功」时 `actual_amount` 必填**，且入账与冲正一律以它为准。

## 5.3 软件接口

### 5.3.1 模拟支付通道

| 项 | 约定 |
|---|---|
| 接口 | `VirtualPaymentGateway.pay(PayRequest)` / `query(String payoutRequestNo)` |
| 请求字段 | **请求号 `payout_request_no`**、业务幂等键 `payment_intent_no`（仅用于对账关联，不参与通道去重）、收款人标识、金额（分）、请求时间 |
| 响应字段 | 结果码、渠道流水号、**实际出款金额 `actual_amount`（`SUCCESS` 与 `AMOUNT_MISMATCH` 时必返；其余情形可为空）**、响应时间 |
| 结果码 | `SUCCESS` / `FAIL` / `TIMEOUT` / `LOST_RESPONSE` |
| 失败原因码 | `GW_BALANCE_INSUFFICIENT`、`GW_ACCOUNT_FROZEN`、`GW_SYSTEM_ERROR` |
| 超时阈值 | 3 秒；超时按 `TIMEOUT` 处理 |
| **幂等** | **同一 `payout_request_no` 重复请求，通道应返回首次结果，不重复扣款**；不同请求号视为两次独立请求 |
| 回调 | 支持异步回调；回调可能重复、可能乱序；回调须携带请求号与业务幂等键 |
| 数据存储 | 通道侧独立维护 `通道流水` 表，应用不得直接修改 |

> **为什么两个号都要传**：`payout_request_no` 保证通道不重复扣款，`payment_intent_no` 让日终对账能把多次尝试归并到同一笔应付上。若只传一个，要么通道无法去重，要么对账无法归并——v1.0 的设计正是在这里把两者混成了一个字段。

**`query` 返回语义（这是三类对账差异能否复现的前提）**

| 通道侧情形 | `query` 返回 | 调用方应做 |
|---|---|---|
| 该请求号已成功，且金额一致 | `SUCCESS` + 渠道流水号 | 按成功入账 |
| 该请求号已明确失败 | `FAIL` + 原因码 | 允许受控重试 |
| 该请求号不存在（从未收到） | `NOT_FOUND` | 判定为未出款，可重试 |
| 该请求号存在但金额与请求不符 | `AMOUNT_MISMATCH` + 实际金额 | 生成差异单，转人工 |
| 查询本身超时 | `TIMEOUT` | 计数 +1，累计 3 次转人工 |

**通道行为模式（配置项 `gateway.mode`）**

| 模式 | 行为 | 用于验证 |
|---|---|---|
| `SUCCESS` | 同步返回成功 | 主流程、AC-01 |
| `FAIL` | 同步返回明确失败，通道不落流水 | 失败重试、AC-02 受控重发 |
| `TIMEOUT` | 不返回，客户端超时；通道**不**记账 | 未知态、查证后判负 |
| `LOST_RESPONSE` | 通道侧记账成功但不返回响应 | **差异②：通道成功 / 本地未知** |
| `DUPLICATE_CALLBACK` | 对同一请求号重复推送成功回调 | 幂等校验、AC-02 |
| `CHANNEL_MISSING` | 本地收到成功但通道侧不落流水 | **差异①：本地成功 / 通道无记录** |
| `AMOUNT_MISMATCH` | 通道按请求金额 ±1 分记账，并返回该金额 | **差异③：金额不一致** |

> `TIMEOUT` 与 `LOST_RESPONSE` 必须在**通道是否记账**上明确区分：前者未扣款、后者已扣款。若两者行为相同，`query` 的 `NOT_FOUND` 与 `SUCCESS` 分支就无法被分别验证，"未知不得重试"这条规则也就无从证明。

### A.3 状态机

> **命名约定**（CR-16）：下列五个状态机分属五个独立对象，状态名不得跨对象复用。接口枚举、审计日志、UI 标签一律带对象前缀，如 `SLOT_PENDING_SETTLE`、`SETTLEMENT_COMPLETED`、`PAYOUT_MANUAL_REVIEW`。
>
> **任务状态是派生量**：它不是独立迁移的，而是由其下 N 个名额的状态集合按优先级投影得出（见 A.3.2）。这一条解决 v1.0 的核心缺陷——若任务按"单个名额的事件"迁移，一个劳动者开始履约就会把整个任务推到「履约中」，而其余名额可能还没被录用。

#### A.3.1 名额（Slot，任务内单个招聘位）

| 当前 | 事件 | 守卫 | 目标 |
|---|---|---|---|
| 待占用 | 录用成功 | 名额可用、非自我交易 | 已占用 |
| 待占用 | 撤单 / 到期下架 | 任务不再招募 | 已释放（不补员） |
| 已占用 | 劳动者开始履约 | 签约有效 | 履约中 |
| 已占用 | 劳动者取消签约 / 未开始自动取消 | — | **待占用（重新开放，清空报名ID 与签约ID）** |
| 履约中 | 提交交付物 | 凭证合法 | 已交付 |
| 已交付 | 验收通过 / 超时自动验收，且实付 > 0 | 无争议 | **待结算** |
| 已交付 | 验收通过 / 超时自动验收，且实付 = 0 | 无争议 | **已完结**（零实付，直接终结） |
| 已交付 | 雇主拒收 / 劳动者申诉 | — | 待裁决 |
| 待裁决 | 发起方撤回争议 | 撤回次数 < 2 | 已交付（重算验收倒计时） |
| 待裁决 | 判定放款 | 管理员 | **待结算** |
| 待裁决 | 出口 B 受控重发（原打款已作废） | 管理员，且通道确认无扣款，且 `attempt_seq < payout.maxAttempts` | **待结算** |
| 待裁决 | 判定退款 | 管理员 | 已退款 |
| 待裁决 | 人工标记失败后选择退款（出口 A） | 管理员 | 已退款 |
| 待结算 | 打款成功 | — | **已完结** |
| 待结算 | 人工标记失败 | 管理员 | 待裁决（待资金处置） |
| **已完结** | **差异① 回退重试**（3.4.6） | **差异单已核实为「本地成功 / 通道无记录」，且打款单已更正为「失败」** | **待结算**（唯一允许从终态迁出的边） |
| 已完结 / 已退款 / 已释放 | 任意**其他**事件 | — | 不变（终态） |

> **「已释放」只表示"这个名额再也不会补员"**，只由「撤单 / 到期」触发。**取消签约不进「已释放」**——若进终态，`FR-SIGN.CANCEL.02` 要求的"再次录用"就不可达，且 N=1 的任务会聚合为「已关闭」，而那笔仍为「已托管」的资金再也没有出口（v1.1 的 P0-01）。取消签约一律回到「待占用」，名额保持开放，托管明细保持「已托管」。
>
> **为什么必须有「待结算」**：v1.0 让名额在验收通过时直接进「已完结」，于是"钱还没到账、名额却已完结"。一旦打款失败转人工退款，就出现"名额已完成但钱退回去了"的孤儿状态。新增「待结算」后，**名额的终态由资金的真实归宿决定**：钱到了劳动者 → 已完结；钱退回雇主 → 已退款。

#### A.3.2 任务（Task，派生）

**任务状态 = f(名额状态集合, 招募开关, 撤单标志)**，按下列优先级取第一个命中的规则。**任务状态只用于展示，不作为业务守卫**——报名、录用、撤单等操作的守卫一律直接判定名额集合与时间（见 FR-SIGN.APPLY.01、FR-TASK.CANCEL.01）。

**招募开关 `recruiting_closed` 是独立属性，不是派生状态**（v1.2 的 P1-02）：

> `recruiting_closed = (撤单标志 = 真) OR (当前时间 ≥ 结束时间)`

它回答"还能不能报新名"，与"任务进行到哪一步"正交。两者必须分开存、分开显示：**状态字段表示进度，开关字段表示是否收口**。若把"到期"塞进状态优先级里，就会出现"到期任务显示「结算中」而不是「已关闭招募」"的矛盾（R7~R10 必然先命中）；若把"到期"做成最高优先级，又会丢失履约进度展示。

| 优先级 | 条件 | 任务状态 |
|---|---|---|
| R0 | 任务为草稿（尚未发布） | 草稿 |
| R1 | 存在「待占用」，**且** `recruiting_closed = 假` | **招募中** |
| R2 | 存在「待裁决」名额，**且**存在未裁决的争议单 | 争议中 |
| R3 | 存在「待裁决」名额，**且**无未裁决的争议单（即由打款人工失败产生） | **结算异常** |
| R4 | 全部名额均为终态（已完结 / 已退款 / 已释放），且撤单标志为真 | 已取消 |
| R5 | 全部名额均为终态，且 ∃ 至少一个「已完结」 | 已完成 |
| R6 | 全部名额均为终态，且无「已完结」 | 已关闭 |
| R7 | 存在「待结算」 | **结算中** |
| R8 | 存在「已交付」 | 待验收 |
| R9 | 存在「履约中」 | 履约中 |
| R10 | 存在「已占用」，无「待占用」，且 `recruiting_closed = 假` | 已接单 |
| R11 | `recruiting_closed = 真`，且存在非终态名额 | 已关闭招募（停止招募，在途名额继续走完） |
| R12 | 兜底 | 已关闭 |

**异常标记字段（与状态并列返回，用于列表角标）**

| 字段 | 条件 | 用途 |
|---|---|---|
| `has_open_dispute` | 存在未裁决的争议单 | 「争议中」角标，即使状态显示「招募中」也可点入 |
| `has_settlement_abnormal` | 存在「待裁决」名额但无争议单 | 「结算异常」角标，指向资金处置入口 |
| `recruiting_closed` | 见上 | 报名按钮置灰的依据 |

> **R1 必须排在 R2/R3 之前**（v1.2 的 P1-01）。多名额任务中，一个名额待裁决、另一个仍「待占用」且未到期时，若 R2/R3 先命中，任务显示「争议中/结算异常」并从"招募中"列表消失；而 `FR-SIGN.APPLY.01` 的守卫只判名额集合，直接链接仍可报名。结果是**用户看不到、却报得上，剩余名额无人补**。把 R1 提到最前 + 独立的异常标记字段，两个问题一起解决：列表仍展示该任务，异常用角标表达。
>
> **R1 必须排在 R7~R10 之前**（v1.1 的 P1-01）。多名额任务中，只要还剩「待占用」且未收口，任务就必须显示「招募中」；否则第一个名额进入履约后，R1 被 R9 压住，剩余名额再也报不上名——这正是 v1.0"单名额事件误推整个任务"的翻版。
>
> **R2 与 R3 必须分开**（v1.1 的 P1-02）。「待裁决」有两个来源：真实争议（有争议单）与打款人工失败（无争议单）。若都显示「争议中」，运营在争议列表里查不到对象，用户看到的"争议中"也无法申诉。分成「争议中」与「结算异常」两个队列，各自有入口。
>
> **R7「结算中」**：名额已验收、只等打款，此时显示「待验收」会让用户以为还要自己操作（v1.1 的 P2-06）。
>
> **R11「已关闭招募」不是终态**。它表示"不再接新报名，但已有名额还没走完"。它排在 R7~R10 之后是**有意的**：到期任务的进度仍要能看见（"履约中且已停止招募"比"已关闭招募"信息量更大），收口信息由 `recruiting_closed` 单独承载。

| **已释放** | **差异① 回退重试**（3.4.6） | **名额已回「待结算」、结算单已回「待重试」** | **释放中**（唯一允许从终态迁出的边） |
| 已释放 / 已退款 | 任意**其他**事件 | — | 不变（终态） |

> **「撤单 / 到期 → 已退款」必须带名额守卫**（v1.1 的 P0-05）。到期时，仍处于「已占用 / 履约中 / 已交付 / 待结算」的名额，其托管明细同样是「已托管」；若不加守卫而一律退款，就会把在途履约的钱退给雇主，之后打款时 `ACC-FROZEN` 无钱可转，直接错账。规则是：**只有名额为「待占用」时，撤单/到期才退款**。
>
> **「释放中 → 已托管」不只是改状态**（v1.1 的 P0-02）。人工标记失败意味着通道确认未出款，此时资金仍在 `ACC-TRANSIT`。若只把托管明细退回「已托管」而不把资金退回 `ACC-FROZEN`，后续出口 A/B 会从已空的冻结余额再扣一次，结果是冻结为负或侵占该用户其他任务的托管金，同时在途永久挂着已退给雇主的钱。
>
> **「已托管 → 已退款」必须是条件更新，不能只判名额**（v1.2 的 P0-03）。用户撤单与整点到期任务是两个独立发起方，可同时读到同一批「待占用」名额与「已托管」明细。账户行锁只能让两笔扣减串行，**不能阻止第二笔**：第二笔仍会从该雇主冻结余额再退一次——余额里若还有其它任务的托管金，就退走了别人的钱。因此退款前必须以 `UPDATE 托管明细 SET 状态='已退款' WHERE ID=? AND 状态='已托管'` 抢占该行，**受影响行数不为 1 时跳过该明细、不再扣冻结余额**，并记审计。

#### A.3.4 结算单

| 当前 | 事件 | 守卫 | 目标 |
|---|---|---|---|
| 待生成 | 验收通过或判定放款，实付 > 0 | 无未裁决争议 | 已确认（自动） |
| 待生成 | 验收通过，实付 = 0 | 无未裁决争议 | 已确认 → 已完结（同事务，见 FR-SETTLE.FEE.03） |
| 已确认 | 发起打款 | 请求号已持久化 | 打款中 |
| 打款中 | 通道成功 | — | 已完结 |
| 打款中 | 明确失败且未超限 | `attempt_seq < payout.maxAttempts` | 待重试 |
| 待重试 | 重试（新打款单） | `attempt_seq < payout.maxAttempts` | 打款中 |
| 打款中 | 人工标记成功 | 填 `actual_amount` | 已完结 |
| 打款中 | 人工标记失败 | 零扣款凭据 | 已作废 |
| 已作废 | 出口 B 受控重发 | **`attempt_seq < payout.maxAttempts` 且通道确认无扣款** | 打款中 |
| 已作废 | 出口 A 退款 | — | 保持已作废 |
| 打款中 | 打款单转「待人工处理」 | — | **保持打款中**（状态不改，由打款单承载"未定"） |
| **已完结** | **差异① 回退重试**（3.4.6） | **原打款单已更正为「失败」，且名额已回「待结算」** | **待重试**（唯一允许从终态迁出的边） |
| 已完结 / 已作废 | 任意**其他**事件 | — | 不变（终态） |

> 结算单不设「待人工处理」——"结果未定"只发生在某一**次**尝试上，属于打款单的语义。v1.0 把该状态放在结算单上，导致管理员在最后一张打款单已是「失败」终态时找不到可操作对象。

#### A.3.5 打款单（每次尝试一条）

| 当前 | 事件 | 守卫 | 目标 |
|---|---|---|---|
| 待执行 | 发起出站 | 请求号已持久化 | 执行中 |
| 执行中 | 通道返回成功 | — | 成功 |
| 执行中 | 通道返回明确失败 | `attempt_seq` < `payout.maxAttempts` | 失败 |
| 执行中 | 通道返回明确失败 | `attempt_seq` = `payout.maxAttempts` | **待人工处理**（无重试额度，直接升级） |
| 执行中 | 通道返回超时 / 无响应 | — | 未知 |
| 执行中 | 崩溃恢复：超过 `payout.stuckMinutes`（默认 10）仍为执行中 | — | **未知**（只能查证，不得重发） |
| 未知 | 查证得 `SUCCESS` | — | 成功 |
| 未知 | 查证得 `FAIL` | — | 失败 |
| 未知 | 查证得 `NOT_FOUND`（通道从未收到） | — | 失败（判定未出款，可进入重试） |
| 未知 | 查证得 `AMOUNT_MISMATCH` | — | **待人工处理**（同时生成差异单） |
| 未知 | 查询 3 次无确定结果 | — | 待人工处理 |
| 待人工处理 | 人工标记为成功（须填依据，**必填 `actual_amount` 且 ≤ 请求金额**） | 通道流水或凭据可核 | 成功（按 `actual_amount` 入账，差额退回雇主） |
| 待人工处理 | 人工标记为失败（须填依据） | **通道流水确认该请求号零扣款** | 失败 |
| 待人工处理 | 转差异处置 | — | 待人工处理（保持，生成差异单交 3.4.6） |
| 未知 / 待人工处理 | 直接重发 | — | **非法，拒绝**（`PAYOUT_PENDING_VERIFICATION`） |
| **成功** | **差异① 定向更正**（3.4.6） | **差异单已核实"通道零出款"并附通道侧凭据** | **失败**（记 `SUCCESS_REVERSED` + 审计 + 告警；唯一允许从终态迁出的边） |
| 成功 / 失败 | 任意**其他**事件 | — | 不变（终态） |

> **一次尝试一张单**：`失败` 是这张打款单的终态，重试意味着**新建一张**打款单并生成新的 `payout_request_no`。这样"重试"与"幂等去重"不再冲突——通道按请求号去重，系统按结算单号保证只成功一次。
>
> **为什么"超限"要直接进「待人工处理」而不是从「失败」再跳**（v1.1 的 P0-04）：`失败` 是终态，不可再迁出。若先置失败再改，管理员在「待人工处理」列表里永远看不到这张单，资金就停在 `ACC_TRANSIT`。所以超限必须在**产生失败的同一次迁移**里判掉。
>
> **为什么必须有「执行中 → 未知」的恢复迁移**（v1.1 的 P0-03）：出站调用不可能与数据库事务原子提交。若进程在"已标记执行中、尚未落结果"之间崩溃，这张单会永远停在「执行中」。恢复任务必须把它当"结果未知"处理——**只能查证，不得重发**。
>
> **「未知」与「待人工处理」的区别只在谁来定性**：前者等通道查证，后者等人工依据流水判定。两者都不允许直接重发。
>
> **人工处置必须有"通道实际金额"这一个输入**（v1.2 的 P0-01）：`AMOUNT_MISMATCH` 意味着通道按 Y 出款而请求金额为 X。若"标记成功"只能按 X 入账，Y 与 X 的差额既无账务归属又无法追回；若"标记失败"按 X 退款，而通道已付出 Y，等于平台再贴一笔。因此「标记成功」强制填 `actual_amount`，「标记失败」强制先取得零扣款凭据——两者都是**把外部事实作为入账前提**，而不是让操作员凭印象选一个终态。
>
> **`待执行` 不是终态**（v1.2 的 P0-04）：它表示"资金已划入在途、单据已建、请求号已持久化，但尚未出站"。唯一出边是由 `FR-JOB.PAYOUT.01` 扫到后发起出站（复用原请求号）。若不实现该扫描任务，`待执行` 就是死状态，资金永久停在 `ACC-TRANSIT`。

#### A.3.6 终态回退：全系统唯一允许的四条边（v1.4 的 P0-02）

> **为什么单列一节**：3.4.6 的「① 本地成功 / 通道无记录 → 冲正 + 回退重试」要求把已经入账的成功单据退回重试，而此前**四个对象都已经在终态**。v1.3 只在文字里承诺"回退"，四张状态机表却没有一条出边——按表实现，这个处置**不可达**。v1.4 把四条边显式写进各表，并在本节集中约束，防止它们被当成通用的"撤销"能力滥用。

| # | 对象 | 当前 → 目标 | 所在表 | 守卫 |
|---|---|---|---|---|
| E1 | 打款单 | 成功 → 失败 | A.3.5 | 差异单已核实"通道零出款"且附通道侧凭据 |
| E2 | 结算单 | 已完结 → 待重试 | A.3.4 | E1 已完成 |
| E3 | 名额 | 已完结 → 待结算 | A.3.1 | E2 已完成 |
| E4 | 托管明细 | 已释放 → 释放中 | A.3.3 | E3 已完成 |

**四条边共有的实现约束**（任一不满足即视为实现错误）：

1. **唯一入口**：只能由差异单的「冲正」处置（3.4.6 情形 ①）驱动，不提供任何其他 API、后台脚本或手工改库入口。
2. **同一事务**：E1~E4 与冲正分录、`在途→冻结` 结转必须在同一事务内完成；任一步失败整段回滚，不允许出现"钱已冲正、单据还是成功"或"单据退回、账没冲正"。
3. **强制留痕**：E1 必须写 `SUCCESS_REVERSED` 审计流水并计入告警；差异单必须记录处置人、依据、通道侧凭据引用。
4. **不可推广**：`失败`、`已退款`、`已释放`（非回退场景）、`已作废` 等其余终态**一律无出边**。附录 E 第 16 项"每个状态都有出口"的例外只限于本节四条边。

> **实现提示**：不要把 E1~E4 写成"反向调用正向接口"。正向路径（A.4 #11）带余额校验、部分唯一索引、幂等键，反向走这些会撞约束。四个回退应当是**独立的、只在这一处被调用的定向更新**，显式指定 `WHERE ID=? AND 状态='<旧状态>'` 并校验受影响行数为 1。

#### A.3.7 其余三个枚举的状态机（v1.4 的 P1-07）

> **为什么补这一节**：报名单、争议单、差异单在数据模型里都给了状态取值，但 A.3.1~A.3.5 只覆盖了五个"资金主对象"。没有迁移表，实现者只能自由发挥，最容易错的是**争议单可以从「已撤回」回到「待裁决」**（`FR-DISPUTE.WITHDRAW.02` 要求复用同一张单）和**差异单在余额不足时必须保持「待处理」**——这两点若不写明，就会分别被实现成"新建一张争议单"和"照常处置、允许透支"。

**报名单（Apply）**

| 当前 | 事件 | 目标 |
|---|---|---|
| 待处理 | 被录用 | 已录用 |
| 待处理 | 名额已满 / 任务撤单 / 已过结束时间 | 已拒绝 |
| 待处理 | 劳动者主动撤回 | 已撤回 |
| 已录用 | 劳动者取消签约、未开始自动取消（A.4 #5 / #6） | 已撤回（与名额清空报名ID同一事务） |
| 已拒绝 / 已撤回 | 任意 | 不变（终态） |

> 同一 (任务, 劳动者) 至多一条**非终态**报名；再次报名新建记录，不复用已拒绝/已撤回的单（`FR-SIGN.APPLY.06`）。

**争议单（Dispute）**

| 当前 | 事件 | 守卫 | 目标 |
|---|---|---|---|
| （无） | 雇主拒收 / 劳动者申诉 | 该名额当前无「待裁决」争议 | 待裁决 |
| 待裁决 | 发起方撤回 | `撤回次数 < 2` | 已撤回（名额回「已交付」、托管明细回「已托管」，见 `FR-DISPUTE.WITHDRAW.01`） |
| 待裁决 | 判定放款 | 管理员 | 已裁决 |
| 待裁决 | 判定退款 | 管理员 | 已裁决 |
| **已撤回** | **同一名额再次发起争议** | **复用同一张单**，`撤回次数` 累加 | **待裁决**（不是新建单） |
| 已裁决 | 任意 | — | 不变（终态） |

> 「同一名额至多 1 张待裁决」由应用层保证（数据模型未用唯一索引约束，因为允许历史多张）。

**差异单（ReconDiff）**

| 当前 | 事件 | 守卫 | 目标 |
|---|---|---|---|
| 待处理 | 处置 = 补记 | 目标科目余额足够 / 借贷平衡 | 已处理 |
| 待处理 | 处置 = 冲正（含 ① 的"冲正 + 回退重试"） | 收款人可用 ≥ `X`；E1~E4 四步同事务 | 已处理 |
| 待处理 | 处置 = 差额调整 | 收款人可用 ≥ `X − Y` | 已处理 |
| 待处理 | 处置 = 忽略并说明 | 须附依据 | 已忽略 |
| 待处理 | 上述任一处置但**余额不足** | — | **保持待处理**并升级告警（**不得透支、不得先记后补**） |
| 已处理 / 已忽略 | 任意 | — | 不变（终态） |

### A.4 跨对象联动（事务边界）

> 本节是全文最容易出错的一处：五个状态机单独看都对，联动漏掉一个就会出现"任务已完成但钱还冻着""钱已放但名额还占着""名额已退款却仍显示完成"。开发时按行实现，验收时按行造用例。
>
> **任务列统一写"重算"**：任务状态是派生量（A.3.2），任何名额变化后都按聚合规则重算，不需要在事务里单独写任务迁移逻辑。

**事务边界的三条规则**（v1.1 的 P0-03）

外部调用不可能与数据库事务原子提交。凡是"要发请求给通道"的事件，必须拆成三段，事件名后用 `T1/T2/T3` 标注：

| 段 | 做什么 | 是否有事务 | 崩溃后的后果与恢复 |
|---|---|---|---|
| **T1 受理** | 生成结算单/打款单、**持久化 `payout_request_no`**、`冻结→在途`、打款单置「待执行」，提交 | 是，单事务 | 提交成功但后续未执行：单据停在「待执行」，由调度器捡起重发，**请求号不变** |
| **T2 出站** | 打款单「待执行→执行中」并**提交**，然后**在事务外**用已提交的请求号调用通道 | 提交状态，调用本身无事务 | 提交后崩溃：单据停在「执行中」，由恢复任务按 A.3.5 转为「未知」并查证，**不得重发** |
| **T3 结果** | 按通道返回落库（成功/失败/未知），同事务更新结算单、名额、托管明细与分录 | 是，单事务 | 落库失败：整段回滚，单据仍在「执行中」，回到 T2 的恢复分支 |

**绝不允许**把 T2 的通道调用包进 T1 或 T3 的事务里。若强行包进去，通道已扣款而事务回滚时，本地既没有打款单也没有请求号，事后连"该查哪一笔"都无法回答。

1. **取消签约回到「待占用」，不是「已释放」**（第 5/6 行）。若进终态，`FR-SIGN.CANCEL.02` 的"再次录用"不可达，且 N=1 的任务会被聚合为「已关闭」，而那笔仍为「已托管」的钱再无出口（v1.1 的 P0-01）。
2. **人工标记失败必须把在途资金退回冻结**（第 22 行，`在途→冻结`）。若分录写"不变"，钱留在 `ACC_TRANSIT`，而第 23/24 行又从 `ACC_FROZEN` 扣一次——冻结变负或侵占其他任务的托管金，同时在途永久挂着已退给雇主的钱（v1.1 的 P0-02）。
3. **受理与出站必须分开**（第 9/10 行、第 27 行 + 第 10 行）。T1 只建单并持久化请求号，T2 才调用通道。任何把通道调用包进业务事务的写法都会在崩溃时产生"通道已扣款、本地无记录"的黑洞（v1.1 的 P0-03）。
4. **超限必须在"产生失败"的同一次迁移里判掉**（第 14 vs 15 行）。打款单「失败」是终态，不能先置失败再跳「待人工处理」，否则管理员看不到它（v1.1 的 P0-04）。
5. **雇主拒收时结算单尚未生成**（第 25 行）。结算单只由「验收通过」或「判定放款」驱动创建（FR-SETTLE.GUARD.01）。
6. **打款未知时托管明细保持「释放中」不回落**（第 12/13 行）。资金已在途，若回落到「已托管」，日终对账会把它当成可重复释放项，造成二次打款。
7. **零实付绝不经在途**（第 20 行）。若照常冻结→在途却没有打款动作，`ACC_TRANSIT` 会留下无出口余额。
8. **判定放款只到「冻结→在途」为止**（第 27 行）。管理员裁定 ≠ 通道成功；入账由第 11/21 行决定。
9. **人工处置必须以"通道实际金额"为入账依据**（第 21 行）。按请求金额入账会让差额失去归属；按请求金额退款会在通道已出款时重复出款。第 21 行贷方有三个对象（收款人 `actual_amount`、平台服务费、雇主差额），三者之和必须等于借方在途的应结金额——这是唯一能让 `AMOUNT_MISMATCH` 保持恒等式为 0 的写法（v1.2 的 P0-01）。

**失败语义（按段区分，不再"整行回滚"）**：

- **T1 / T3**：任一步骤失败整段回滚，不留中间态。
- **T2**：不适用回滚——调用已发出，无法撤回。按 A.3.5 的「执行中→未知」处理，只查证不重发。
- **跨段推进**：必须由单据状态驱动（如 T1 后单据为「待执行」才进 T2），不得靠定时任务推断或重放整行。

## 9.4 附录 D：关于"定金 + 尾款"的决策说明

立项讨论中曾考虑"发布时冻结定金、验收前补尾款"的两段付款模式。本版**不采用**，理由如下：

1. **尾款脱离托管会削弱核心价值**。若尾款在交付后才收取且不经托管，劳动者交付后雇主拒付，系统无从处置——而这恰是本系统要解决的第一类风险。
2. **两段托管会引入新的争议类型**。"劳动者已交付、雇主未补尾款"这一状态，既不能放款也不能退款，只能挂起，与"争议仅支持全额放款/退款"的约束冲突。
3. **全额托管让"钱先到位"成为不变式**，争议只需判断"该给谁"，不需判断"钱还在不在路上"，异常流数量显著减少。

**若后续需要定金模式**，最小改动集为：
- 新增托管明细字段 `期次`（DEPOSIT / FINAL）
- 新增状态：任务「待补尾款」、托管明细「部分托管」
- 新增需求：尾款托管超时 → 劳动者可无责取消并全额退回定金
- 新增判定表规则：尾款未托管时禁止进入「已交付」
